# Архитектура и план перехода

Приложение переводится на модульный монолит с hexagonal-архитектурой по одному законченному сценарию. Flask, существующая схема SQLite и формат invest.enc сохраняются на первом этапе.

## Реализовано

- `wealth_manager/modules/accounts/domain.py`: Account, Purchase, проверки значений.
- `modules/accounts/application.py`: SaveAccount, включая покупку недвижимости и снимок стоимости.
- `modules/accounts/ports.py`: интерфейсы репозитория и UnitOfWork.
- `modules/preferences/application.py`: ChangeLanguage и порты настроек.
- `adapters/persistence/sqlite.py`: реализации портов для существующей схемы.
- `adapters/persistence/unit_of_work.py`: одна операция записи с восстановлением памяти при ошибке; успех возвращается после сохранения зашифрованного файла.
- `bootstrap.py`: сборка сценариев, хранилища и runtime.
- `factory.py`: `create_app(config=None, *, vault=None)`, независимый экземпляр Flask.
- `adapters/runtime.py`: явные `start()` / `close()`, остановка и ожидание фонового потока.
- `adapters/web/security.py`: блокировка соединения на время запроса, guard, legacy-сохранение и освобождение блокировки.
- `adapters/web/legacy_routes.py`: регистрация существующих обработчиков с зависимостями конкретного экземпляра; оставшиеся lifecycle/auth-настройки и форматирование экспорта.
- `adapters/web/i18n.py`, `locales/en.json`: переводы интерфейса; русский — исходный язык, английский — каталог.
- «Настройки → Общие»: выбор языка, сохраняемый в зашифрованной базе. Смена языка не меняет названия, заметки и значения существующих классификаторов.

Зависимости: входной HTTP-адаптер → application → domain/порты. Исходящие адаптеры реализуют порты; bootstrap связывает реализации. В ядре нет Flask, SQLite и Vault.

Пакет находится рядом с app.py, чтобы сохранить запуск `python app.py` без установки пакета. Фабрика приложения уже реализована; переход к src-layout пока не выполнялся.

## Этап 1: завершённый каркас приложения

`app.py` — точка входа и экспорт фабрики. Импорт не создаёт Flask/Vault и не запускает поток. `db.py` содержит только схему и миграции, без глобального соединения, `set_vault` и путей из окружения. Каждый экземпляр получает отдельные Vault, сценарии, ключ сессии и runtime в `app.extensions["wealth_manager"]`.

Параметры фабрики: `VAULT_PATH`, `LEGACY_DB_PATH`, `IDLE_MINUTES`, `AUTOLOCK_POLL_SECONDS`, стандартные Flask-параметры. Переменные окружения `INVEST_VAULT`, `INVEST_DB`, `INVEST_IDLE_MIN` читаются при создании приложения; явная конфигурация имеет приоритет. Объект Vault можно передать в фабрику для тестирования адаптера.

Фабрика не открывает хранилище и не запускает фон. `runtime.start()` явно запускает единственный поток автоблокировки; повторный вызов безопасен. `runtime.close()` выставляет Event остановки, ожидает поток, сохраняет и закрывает Vault; повторное закрытие безопасно. После успешного закрытия runtime повторно не запускается, запросы получают 503. При сбое записи ошибка передаётся владельцу, база остаётся доступной для повторного сохранения. Владелец вызывает close вне HTTP-запроса, чтобы не ждать поток, удерживая нужную ему блокировку.

`python app.py` управляет runtime через try/finally и отключает reloader. При использовании фабрики другим сервером жизненным циклом управляет этот сервер/его обёртка. Без явного start сохраняется проверка таймаута на защищённых HTTP-запросах, но нет фоновой блокировки в отсутствие запросов.

Локализация выбирает язык и предоставляет переводы. Синхронизация запросов находится только в security.py. Обработчики регистрируются заново для каждого экземпляра и замыкают только его зависимости. Существующие URL и названия endpoints сохранены.

## Этап 2: операции и чистые расчёты

Завершён. `adapters/web/commands.py` разбирает формы и вызывает сценарии; SQL и сохранение файла находятся за портами. Существующие URL, endpoints, форма базы и RU/EN сохранены.

- `modules/accounts/commands.py`: оценка, архивирование, удаление счёта, историческая стоимость.
- `modules/positions`: позиции, нормализация денежных позиций, ручное и пакетное обновление цен.
- `modules/cashflows`: ручные операции, получение дохода, защита операций, принадлежащих арендному платежу.
- `modules/rentals`: договоры, расписание, статусы платежей и синхронизация доходов. Платёж, доход и снимок сохраняются одним UoW. Редактирование договора обновляет источник и счёт связанных доходов; сокращение договора удаляет будущие ожидаемые платежи и обрезает пересекающиеся периоды без создания периода с концом раньше начала.
- `modules/valuation/domain.py`: чистые курсы/конвертация, XIRR и метрики счёта; `modules/rentals/metrics.py`: просрочка, курсовая разница, занятость недвижимости. Дата расчёта передаётся явно.
- `shared/ports.py`: контракты операций; `adapters/persistence/operations.py`: SQLite-реализации. `bootstrap.build_services(..., today=...)` позволяет задавать часы сценариев в тестах.

`calc.py` сохраняет совместимый API: загружает данные для расчётов и передаёт их чистому ядру. На этапе 3 агрегирование отчётов и внешние поставщики также вынесены в отдельные модули. Миграция REAL на Decimal не входит в этап 2.

Некорректные даты, статусы и нечисловые значения NaN/Infinity отклоняются. Обращение к отсутствующей изменяемой сущности возвращает 404; нарушение формата — 400. Исторический разбор текстовых числовых полей с заменой непарсящегося текста на ноль пока сохранён. Пакет цен ограничен указанным счётом, чужие/отсутствующие позиции игнорируются как прежде.

## Транзакции и ограничения переходного этапа

Все перенесённые операции со счетами, позициями, денежными потоками, арендой и смена языка используют VaultUnitOfWork. Под блокировкой хранилища создаётся резервная копия SQLite **в памяти**. При исключении восстанавливается исходная база. Запись покупки и снимка стоимости входит в тот же сценарий. Незашифрованных временных файлов не создаётся.

Все HTTP-запросы удерживают RLock хранилища до teardown, включая сохранение в after_request: это защищает общее SQLite-соединение от автоблокировки и одновременных запросов. Новые сценарии повторно используют тот же RLock. Для локального приложения сериализация запросов приемлема; длительный сетевой запрос временно откладывает автоблокировку.

Lifecycle/auth-настройки пока используют legacy-сохранение after_request. Курсы и источники котировок используют UoW. Переносимые сценарии обязаны использовать UoW; нельзя начинать его внутри уже открытой транзакции. `calc.take_snapshot(..., commit=False)` — временный адаптер к старым расчётам. Открытие дашборда и других отчётов теперь ничего не записывает. Снимки создаются при изменении данных; отдельного ежедневного планировщика пока нет.

Account использует Decimal на входе, но SQLite-адаптер преобразует суммы в REAL для совместимости. Это **не завершённая миграция денежной точности**: переход всей схемы на Decimal/text требует отдельной миграции и проверки расчётов.

## Этап 3: отчёты и источники данных

Завершён. `modules/reporting` строит дашборд, карточки счетов, доходы, историю и списки операций из отсоединённых записей через `ReportRepository`. SQLite-адаптер читает согласованный набор таблиц под блокировкой. Для текущего локального объёма данных это простой полный снимок; при росте объёма порт можно заменить специализированными выборками. Входные GET-обработчики не делают SQL и не создают снимки стоимости. CSV получает записи через тот же порт.

`modules/market_data` содержит порты криптокотировок, MOEX, ЦБ, курсов и региональных предпочтений. `adapters/market_data/providers.py` реализует только публичное чтение по фиксированным адресам: таймаут 10 секунд, ограничение ответа 2 МБ, проверка тикеров и конечных положительных цен. Получение данных завершено до открытия UoW записи. Общая HTTP-блокировка приложения пока удерживается на время запроса, как в этапе 1; это не фоновый загрузчик.

Успешные котировки записываются одной операцией вместе со снимком; отсутствующие цены не обнуляют позиции. Пользователь видит число обновлений, отсутствующие тикеры и источники. ЦБ учитывает номинал валюты. Криптопары к USDT по-прежнему оцениваются через USD с явно указанным приближением USDT≈USD; остальные стейблкоины запрашиваются по рыночной цене, а не фиксируются равными единице.

### Страна и криптобиржи

В настройках добавлен раздел «Страна и криптобиржи»: код страны проживания ISO, предварительный просмотр бирж, выбор источников и сохранение. GET-просмотр другой страны не меняет рабочий профиль. В `settings` хранятся `country` и независимые `crypto_exchanges:<COUNTRY>`; изменение страны не удаляет старый профиль. Язык интерфейса от страны не зависит.

После обновления нужно один раз выбрать страну и биржи. Отсутствие выбора означает отсутствие автоматических запросов криптокотировок. Резервные запросы допускаются только к выбранным источникам; исключения из справочника проверяются и при сохранении, и перед запросом. Ручной ввод цен доступен всегда. Это настройка источников котировок, без торговых операций, API-ключей и определения страны по IP.

Справочник `adapters/market_data/exchanges.json` содержит отдельные идентификаторы провайдеров, исключённые страны, страны с частичными ограничениями, дату проверки и первичные источники. Изменение ограничений не требует изменения расчётов/адаптеров API. Начальная проверка: 10.11.2026. Binance исключён из профиля RU. Bybit/OKX не маркируются как гарантированно доступные: UI различает исключение, ограничения отдельных услуг и необходимость проверить условия. Неизвестная страна не получает автоматически выбранных бирж. Справочник не исчерпывает региональные ограничения, гражданство, тип услуг и юридические лица бирж; обновляется вручную после проверки первичных источников.

Источники начального справочника:
- Binance: https://www.binance.com/en/blog/all/8578760889994024403
- Bybit: https://www.bybit.com/en/help-center/article/Service-Restricted-Countries
- OKX: https://www.okx.com/help/risk-compliance-disclosure

Тесты используют подставные ответы API и проверяют выбор страны, запрет скрытого fallback, изменение правил, отдельные профили и восстановление после перезапуска, ошибки API, номиналы ЦБ, MOEX, атомарность записи, неизменность базы при чтении, группировки доходов и forward fill истории. Живые биржевые API не вызываются в CI. Browser E2E в этот этап не входит.

## Этап 4: счета, активы и источники дохода

Завершён, версия схемы — 4. Доменные модели и сценарии сохранения разделены:

| Модель | Таблица | Специализированные поля |
|---|---|---|
| `Account` / `SaveFinancialAccount` | `financial_accounts` | broker / crypto / other, организация |
| `Asset` / `SaveAsset` | `assets` | недвижимость, текущая стоимость, адрес |
| `IncomeSource` / `SaveIncomeSource` | `income_sources` | фриланс, ставка налога, площадка |

`entities` хранит общие идентификатор, тип, название, валюту, заметку, архивный статус и дату создания. Это реестр идентичности, а не универсальная бизнес-модель. Репозитории отдельных сущностей реализуют свои порты; общий `EntityRepository` обслуживает архивирование, удаление и историческую оценку. Перевод существующей сущности в другой класс запрещён. Тип брокер/крипто/прочее внутри финансового счёта менять можно.

`leases.asset_id` ссылается на `assets`, а платежи продолжают ссылаться на договор. Новые позиции разрешены только на финансовых счетах. Исторические необычные позиции, которые раньше могли быть прикреплены к недвижимости, сохраняются: FK `holdings.account_id` пока указывает на реестр `entities`, но сценарий создания проверяет финансовый счёт. Денежные потоки и снимки также ссылаются на общий реестр; имя их поля `account_id` сохранено как совместимый идентификатор владельца, оно больше не означает только финансовый счёт. Эта совместимость не создаёт дубликатов сумм.

`accounts` теперь **представление только для чтения**, собирающее прежнюю форму записи из трёх таблиц. Его используют совместимые отчёты и старые ссылки `/accounts/<id>`. Новые ссылки недвижимости и источников дохода — `/assets/<id>` и `/income-sources/<id>`, с отдельными POST-сценариями. `RecordDraft` и `SaveAccount` оставлены как явный адаптер старой формы команды; доменная модель `Account` больше не содержит оценку недвижимости и налоговую ставку фриланса. Старые HTTP-команды архивирования/удаления работают через общий реестр. В боковом меню и формах сущности разделены, RU/EN сохранены.

### Миграция и сохранность данных

- Идентификаторы сохраняются. `legacy_entity_map` фиксирует соответствие старой записи новой сущности; новые ID монотонны и не переиспользуют удалённые значения.
- Старые записи целиком сохраняются в `legacy_accounts_v3` внутри того же зашифрованного файла. Это архив исходных полей для проверки миграции, а не источник текущих данных. При удалении сущности её архивная запись тоже удаляется.
- Суммы, позиции, операции, снимки, договоры и платежи переносятся без пересчёта; связь аренды переименовывается в `asset_id`. Проверяется `foreign_key_check`.
- Смена схемы и её версия фиксируются транзакционно. Подготовка более старой схемы также защищена копией SQLite в памяти. Повторный запуск безопасен.
- При разблокировке миграция сохраняется в зашифрованный файл до выдачи доступа. При сбое восстанавливается база в памяти; исходный файл остаётся прежним, хранилище закрывается. Повторная попытка снова выполняет миграцию.
- Неизвестный старый тип, потерянная FK-связь или договор, привязанный не к недвижимости, останавливают переход без потери исходных данных. Такие записи нужно исправить в старой версии перед повторной попыткой; приложение не переопределяет их смысл автоматически.

Миграция не переводит REAL в Decimal и не добавляет портфели/цели. Обратная миграция к схеме 3 не реализована: старую версию приложения нельзя использовать для записи в обновлённую базу. Перед обновлением рекомендуется сохранить штатную зашифрованную резервную копию через интерфейс.

Тесты сравнивают записи и расчёты до/после обновления с v3, проверяют переход с v1, повторное открытие, соответствие ID, каскады удаления, запрет смены класса, тип владельца позиции/договора, ошибки SQL и диска, повторный вход после ошибки миграции, отдельные формы и локализацию. Node-тест проверяет выбор endpoint и блокировку смены класса при редактировании.

## Целевая навигация

1. Дашборд — reporting, агрегированные данные без собственной копии активов.
2. Макроэкономика — определения показателей, значения за период, дата публикации и источник; интерпретация цикла отдельно.
3. Портфели — состав, доходность, распределение позиций, одна обязательная цель на портфель.
4. Активы — инструменты, недвижимость, позиции и оценки.
5. Компании — эмитенты, список наблюдения, отчётность и заметки; компания может существовать без принадлежащих пользователю бумаг.
6. Доходы — работа, фриланс, инвестиционные поступления и аренда.
7. Налоги — события, расчёты по периоду/юрисдикции, уплаты, вычеты и документы.
8. Настройки — Общие (язык и предпочтения профиля), Счета, Цели, Данные и безопасность.

Эти новые бизнес-разделы описаны как целевая модель; пустые страницы и фиктивные функции в текущий интерфейс не добавляются.

## Этап 5: цели и портфели

Завершён. `modules/planning` содержит Goal, Portfolio, команды и независимую от инфраструктуры модель прогресса. Порты PlanningRepository и PlanningReader реализованы SQLite-адаптерами; сборка — в bootstrap, запись — через общий VaultUnitOfWork. HTTP-адаптер не содержит SQL.

«Настройки → Цели» позволяет создавать, изменять и удалять глобальные цели: название, сумма, валюта, необязательный срок и заметка. «Портфели» в главном меню ведёт к списку и составу портфелей. У портфеля ровно одна цель (`goal_id NOT NULL`), у цели может быть несколько портфелей. Привязанную цель нельзя удалить без переназначения или удаления её портфелей. RU/EN распространяется на формы и сообщения ошибок.

Распределение задаётся **процентом текущей позиции или недвижимости**, с шагом 0,01%. В SQLite хранится целое число базисных пунктов, сумма по всем портфелям не превышает 10 000. Проверка выполняется внутри UoW и дополнительно триггерами INSERT/UPDATE. Изменение доли заменяет прежнее значение. Финансовые счета целиком и источники трудового дохода не распределяются. Дашборд продолжает считать исходные активы: распределение не создаёт капитал, операции или снимки.

Стоимость доли следует за текущим количеством и ценой позиции либо оценкой недвижимости. Это текущая оценка, не история пополнений и не расчёт доходности портфеля. Прогресс цели — сумма связанных портфелей в валюте цели / целевая сумма. Курсы пересчитываются через рубль; для одинаковой валюты конвертация не нужна. При неизвестном или некорректном курсе итог и прогресс не рассчитываются. Срок цели хранится как ориентир, прогноз доходности не выполняется.

Архивирование источника сохраняет распределение и резерв доли, но исключает его стоимость; восстановление возвращает оценку. Новое распределение архивных активов и коротких позиций запрещено. Удаление распределённой позиции, недвижимости или её счёта требует сначала убрать распределение. Удаление портфеля освобождает доли и сохраняет исходные активы.

Миграция v4 → v5 добавляет goals, portfolios, allocations, ограничения и индексы, не изменяя финансовые данные. Старые версии проходят всю цепочку с восстановлением базы в памяти при сбое. Автоматических целей и портфелей не создаётся. Сохранение по-прежнему зашифровано, включая формат SQL-dump Python 3.9. Проверяются ограничения, CRUD, межпортфельная изоляция, валюты, архив, отсутствие двойного учёта, откат при сбое диска, миграция и повторное открытие заполненного хранилища.

## Этап 6: компании, макроэкономика и налоги

Завершён базовый ручной сценарий трёх независимых модулей: `modules/companies`, `modules/macroeconomics`, `modules/taxes`. Каждый имеет свои модели, проверки, команды, порты хранилища и чтения. `adapters/persistence/research.py` реализует SQLite-хранилища и отделённые модели чтения; HTTP-адаптер содержит только разбор форм и вызовы сценариев. Все записи выполняются через VaultUnitOfWork с сохранением зашифрованного файла и откатом при ошибке. Проверка границ ядра запрещает зависимости от Flask, SQLite и адаптеров.

- **Компании:** создание, редактирование и удаление списка наблюдения; название, тикер и биржа (необязательная пара), страна, сектор, сайт, инвестиционная идея; статусы наблюдения, наличия в портфеле и архива. Пара тикер/биржа уникальна без учёта регистра. Статус задаётся вручную и не изменяет позиции. Сайт допускает только HTTP(S), пользовательский текст экранируется.
- **Макроэкономика:** пункт сразу под дашбордом. Наблюдения по стране, показателю и дате; обязательный источник, значение и заметка. Поддержаны ключевая ставка, ставка рефинансирования, ИПЦ и ВВП год к году, доходности государственных облигаций на 2 и 10 лет. Это две точки кривой, а не полная кривая доходности. Последнее значение, дата и изменение в процентных пунктах рассчитываются отдельно для каждой пары страна/показатель; история доступна для редактирования. Повтор даты не перезаписывает наблюдение. Дата — дата показателя либо конец отчётного периода, не дата публикации.
- **Налоги:** ручной журнал базы, ставки и уплаты; оценка `база × ставка / 100` с округлением до двух знаков HALF_UP. Для диапазонов ставок вводятся отдельные строки. Год, страна и валюта образуют независимые группы итогов: без неявного пересчёта валют, смешивания лет или автоматического извлечения данных из доходов. Отрицательный остаток означает переплату.
- **Вычеты:** расходы, вручную указанная сумма возврата, категория, реквизиты/место хранения документов, заметка и статусы от сбора документов до получения или отказа. Полученные и ожидаемые возвраты показаны отдельно, отказ исключён из ожидаемых. Вычеты не уменьшают налог и не создают доходы автоматически. Сами файлы документов в этой версии не загружаются.

Значения хранятся как текст Decimal; суммы ограничены диапазоном 0–10^18, ставки — 0–100%, макрозначения — ±10^6%. Нулевая ставка допустима, пропущенная ставка или значение показателя — ошибка. Даты имеют канонический формат YYYY-MM-DD для одинакового поведения Python 3.9/3.12. В этой версии нет загрузчиков компаний/макроданных, нормативного расчёта налогов и автоматических рекомендаций по инвестиционному циклу.

Миграция v5 → v6 добавляет четыре таблицы и ограничения уникальности, не изменяет существующие счета, цели, портфели и денежные потоки. Ошибка на любом шаге цепочки миграций восстанавливает исходную базу. Формат шифрования и SQL-dump для Python 3.9 сохранены. Тесты проверяют CRUD, ограничения, раздельные итоги, точность округления, источники и даты, RU/EN, экранирование, заблокированное хранилище, откат записи и повторное открытие.

## Локализация

Шаблоны используют `_('Исходный текст')`; JavaScript получает каталог через безопасный `tojson`. Английские подписи для asset_class не меняют передаваемые русскоязычные legacy-значения. Для нового языка нужны каталог, добавление к поддерживаемым языкам и пункт выбора. В заблокированном приложении используется язык текущей подписанной сессии; после перезапуска сервера до разблокировки может отображаться русский, затем язык восстанавливается из хранилища.

Сообщения новых рыночных сценариев переводятся через каталог RU/EN; тексты ошибок внешних API не выводятся напрямую. Сохранённые пользовательские категории остаются на исходном языке.
