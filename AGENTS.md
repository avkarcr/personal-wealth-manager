# Контекст и правила работы с Personal Wealth

Проект `personal-wealth-manager`, пользовательское название «Капитал»: локальный учёт личных инвестиций, доходов, недвижимости, обязательств и целей; аналитика макроэкономики РФ и отраслей. Репозиторий: `avkarcr/personal-wealth-manager`.

## Начало новой сессии

**Репозиторий — основной источник проектного контекста. История предыдущих чатов не требуется.**

1. Прочитай этот файл и [текущий статус](docs/macro-automation/status.md). Сверь фактическую ветку, HEAD и пользовательские изменения: `git status --short --branch`, `git log -5 --oneline`. Статус в документе — датированный снимок, не замена проверке Git.
2. Прочитай [архитектуру](ARCHITECTURE.md) в части задачи, соответствующий пункт [плана М1–М12](docs/macro-automation/plan.md) либо [бизнес-плана](docs/roadmap.md), затем нужный тематический документ и код.
3. Кратко обозначь объём работы. Начинай только задачу, разрешённую пользователем. Команда на конкретный этап уже является разрешением; повторное подтверждение того же объёма не нужно.
4. Не анализируй весь репозиторий и не загружай всю документацию для каждой задачи. Читай зависимости по необходимости; сначала используй `rg`/`rg --files`. Не повторяй чтение неизменённых файлов и уже успешные проверки без причины; ограничивай логи. Экономия контекста не оправдывает снижение качества.

## Постоянные требования

- Общайся по-русски, кратко, простыми фразами; сохраняй английские технические термины. Объясняй результат, проверку и реальные ограничения.
- Развивай существующее приложение и компоненты. Сохраняй стиль, читаемость таблиц, адаптивность desktop/mobile, светлую/тёмную темы, keyboard/focus/hover и понятные состояния загрузки, ошибки и отсутствия данных. Размещение блоков выбирай по текущему UI; фиксированного обязательного порядка блоков нет.
- Поддерживай RU/EN для новых экранов, ошибок, объяснений и встроенных классификаторов. Не переводи и не переписывай пользовательские названия/заметки. Язык и страна — независимые настройки.
- Цели глобальны в настройках; у портфеля ровно одна цель, несколько портфелей могут относиться к одной цели. Распределение активов не создаёт дополнительный капитал.
- Список источников криптокотировок зависит от выбранной страны. Используй существующий справочник и явный выбор; не делай скрытый fallback на исключённые/невыбранные биржи. Актуальность условий провайдера проверяется отдельно.
- Нельзя подменять отсутствие цены, курса, показателя или публикации нулём, единицей либо вымышленными данными. Ноль и неизвестность различаются. Не обещай неподключённый источник или непройденную проверку.
- Капитал, операции, связи, ID и пользовательские данные сохраняются при расширениях. Без необходимости не меняй несвязанную бизнес-логику и не выполняй общий рефакторинг.

## Архитектура и качество

- Модульный монолит с hexagonal-границами: web/файловый адаптер → application → domain/порты; persistence/HTTP реализуют порты; сборка в `wealth_manager/bootstrap.py`. Ядро не импортирует Flask, SQLite, Vault или адаптеры.
- Повторно используй существующие сценарии, карточки, репозитории и read models. Не создавай второй каталог компаний, вторую систему настроек или новое хранилище без обоснованной задачи.
- Денежные расчёты — `Decimal`, хранение — десятичный текст; округление на границе представления. Исключения для XIRR, координат графиков и методов аналитики описаны в архитектуре.
- Изменения сохраняй через `VaultUnitOfWork`, с откатом памяти при ошибке шифрованной записи. Миграции атомарны, сохраняют идентичность и старые данные; учитывай Python 3.9 SQL-dump и повторное открытие vault.
- Читающие отчёты не записывают снимки/операции. Сеть и парсинг не должны попадать внутрь UoW. Макрозагрузки освобождают vault lock и проверяют поколение сессии перед записью; фоновая работа не продлевает разблокировку.
- Модели детерминированы и объяснимы; исходные наблюдения, ревизии, настройки и результаты различаются. Изменение формул/профилей требует версии алгоритма. Подробные правила — в [ADR](docs/macro-automation/decisions.md) и документах этапов.
- Не добавляй секреты, личные финансовые данные, реальные vault, выгрузки или приватные параметры в Git, логи и скриншоты. Синтетические данные помечай как тестовые.

## Проверки

Тестирование выполняется в каждом этапе, а не откладывается на М12. Проверяй изменённое поведение, бизнес-инварианты, миграции, ошибки данных/записи и интеграционные границы. Не добавляй бессодержательные тесты, копирующие реализацию. Для правок только документации достаточно проверки фактов, ссылок и diff; менять тесты не нужно.

Для этапа с кодом используй действующий [CI](.github/workflows/tests.yml):

```bash
python -m pip install -r requirements-dev.txt
python -m coverage run -m unittest discover -s tests -v
python -m coverage report
python -m coverage report --include='wealth_manager/*' --omit='wealth_manager/adapters/web/legacy_routes.py' --fail-under=95
node --check static/app.js
node --check static/macro_charts.js
node --test tests/*.cjs
```

Порог 95% применяется к пакету без `legacy_routes.py`; общий отчёт включает legacy. Процент не заменяет проверку полезности сценариев. CI: Python 3.9/3.12, Node 22, Ubuntu 22.04. Тестовые сценарии не вызывают live API; реальные контрактные фикстуры и синтетические данные различаются. Live-проверки поставщиков выполняются отдельно, ограниченно и с датой результата.

Для затронутого UI выполни соответствующий Chromium-сценарий. `PYTHONPATH=tests:. python tests/ui_wealth.py` проверяет первый запуск, учёт активов, повторный вход и язык отчёта по недвижимости. Тем же способом запускаются `tests/ui_macro_dashboard.py`, `tests/ui_market_catalog.py` и `tests/ui_sector_scoring.py`. CI устанавливает Playwright и Chromium и публикует скриншоты трёх аналитических сценариев.

Полный аудит и оптимизация тестов выполнены после М12. Инвентаризация, результаты измерений и подтверждённые исправления приведены в [отчёте об аудите](docs/test-audit.md).

## Git, этапы и завершение

- Текущая рабочая ветка макроавтоматизации: `feature/macro-dashboard-automation`. Не переходи на `main`, не сливай ветки и не коммить в `main` без отдельной команды. Перед публикацией сверяй удалённую вершину; не перезаписывай чужие изменения и не делай force push.
- В коммит включай только изменения задачи. Сохраняй посторонние пользовательские правки. Делай законченный коммит с понятным сообщением, публикуй в разрешённой рабочей ветке и проверяй CI. Если push/CI недоступны, точно укажи, что осталось неподтверждённым.
- Один согласованный этап — одна завершённая задача. Внеплановая правка UI или передача контекста не разрешает следующий этап. **Не переходи к следующему этапу без команды пользователя.** Слияние и аудит тестов — самостоятельные действия.
- В конце обнови статус, пункт плана, результат этапа и ADR при изменении решения. Не дублируй формулы и списки ограничений в нескольких местах: используй ссылки на владельца информации.
- При прерывании запиши в `status.md`: ветку/HEAD, незавершённые файлы и действия, выполненные проверки, оставшиеся риски и точный следующий шаг. Не отмечай этап завершённым без подтверждения.
- Итог пользователю: результат, ограничения, проверки, коммит/ветка, статус push/CI и следующий шаг. После завершения остановись.
